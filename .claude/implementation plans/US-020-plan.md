## 1. Entendimiento

### 1.1 Contexto — por qué ahora y qué hay ya

`US-020` es la **primera operación de listado** del sistema y la puerta de entrada de `EP-07`: sin la cola, no hay nada que aprobar (`US-021`/`US-022`) ni pantalla que construir (`US-023`). También es el proveedor de datos de `S-04` (`US-024` depende de ella). Hallazgos de grounding, todos verificados contra `main` (`47a58d7`):

- **`IRequestRepository` está esperando exactamente esto.** Su doc-comment dice verbatim: *"Listing operations arrive with their first consumer (US-020, US-015 plan D8)"*. Hoy tiene solo `GetByIdAsync` y `Add`. Y `SAD.md` §6.3 ya trae el **sketch literal del puerto crecido**:
  ```csharp
  Task<IReadOnlyList<Request>> ListOwnedByAsync(EmployeeId owner, CancellationToken ct);
  Task<IReadOnlyList<Request>> ListPendingForManagerAsync(EmployeeId manager, CancellationToken ct);
  ```
  Dos métodos con nombre de intención de negocio, devolviendo agregados — sin `IQueryable` (`CA-APP-005`), sin `IRepository<T>`. El filtro por manager (join `Requests → Employees` sobre `ManagerId`) vive **dentro de `RequestRepository`**, nunca en el handler.
- **El handler ya tiene nombre asignado**: `SAD.md` §6.1 lista `ListVisibleRequestsHandler.cs` en `Application/Requests/`. No hay que inventarlo.
- **`ICurrentUser` ya expone `Role`** (verificado: `EmployeeId` + `EmployeeRole Role`), derivado del claim `ClaimTypes.Role` de la cookie en `CurrentUserAccessor` (Api) — **jamás de un parámetro del cliente**, que es exactamente lo que `AC5` y `FR-AUT-010` exigen. `EmployeeRole` es `{ Employee = 1, Manager = 2 }`.
- **La asignación de manager ya está modelada**: `Employee.ManagerId` (`EmployeeId?`, nullable), poblada por `AssignManager` — cuyo único llamador en el MVP es el seeder (`TE-003`). `AssignManager` **prohíbe ser manager de uno mismo** (`CannotBeOwnManager`), lo que hace estructuralmente imposible que la consulta de cola devuelva solicitudes propias (base de `AC4`, reforzada en `D6`). Seed (`Backlog.md` §3.6): Carlos Ruiz y Ana Torres asignados a Laura Méndez (`manager@vacaflow.test`); Laura no tiene manager.
- **`IEmployeeRepository` no tiene consulta por manager ni por lote** — solo `EmailExistsAsync`, `GetByEmailAsync`, `GetByIdAsync`, `Add`. El nombre del empleado (`employee.fullName` del contrato §6.3) obliga a crecerlo (ver `D7`).
- **`IAbsenceTypeRepository`** tiene `ListActiveAsync` y `ExistsActiveAsync`. El contrato pide `absenceType: { id, code, name }` por solicitud; `ListActiveAsync` **no sirve** para solicitudes históricas cuyo tipo fue desactivado — hace falta una consulta por ids (ver `D7`).
- **El índice ya existe**: `RequestConfiguration.cs:63` crea `(OwnerId, State)` (columna `EmployeeId`), que `SAD.md` §7.2 anota verbatim: *"The index on `(EmployeeId, State)` serves both list queries of `FR-VIS-001`"*. **Cero cambios de esquema.**
- **El contrato de respuesta está fijado por el FRD** (§6.3, verbatim): `[{ id, absenceType: { id, code, name }, startDate, endDate, reason, state, employee: { id, fullName }, createdAtUtc, approval?: { … } }]` con la nota *"The `employee` block is present so a manager can see whose request it is; for an employee it is always themselves."* El bloque `approval?` es **inproducible hoy**: el agregado `Approval` no existe (llega con `US-021`) y los estados `Approved`/`Rejected` son inalcanzables — ver `D8`.
- **`FR-VIS-001` resuelve la semántica del manager** (verbatim): *"**Manager** — the `Submitted` requests of the employees assigned to them, **plus their own requests as an employee**. The caller cannot influence this through parameters."* Es decir: la respuesta del manager es la **unión** cola + propias; "la cola" (`AC2`–`AC4` hablan de *my queue*) es el subconjunto que `S-07` renderiza. Ver `D3` — es la decisión central del plan.
- **GET /requests no tiene errores de negocio**: el único error posible es `VF-AUT-004` `401` (endpoint protegido, `FR-AUT-011`). **`ErrorStatusMap` no cambia** — segunda historia consecutiva sin tocar el catálogo.
- **Patrones vigentes que este plan hereda**: handlers `sealed` sin mediator (`ADR-002`), inyectados directo en el endpoint; DTO propio por caso de uso con mapeo manual (`CA-APP-006`/`CA-APP-011`, precedente `RequestDetailDto`/`AuthenticatedUserDto`); `State` viaja como nombre del enum (`ToString()`, labels de §3.4); endpoints "reciben, delegan, mapean" con `.RequireAuthorization()` explícito (test de arquitectura lo exige); repositorios `internal sealed` con `AsNoTracking` implícito no usado aún — las lecturas de lista lo estrenan (`D5`).
- **Web**: no existe `(app)/queue/page.tsx` ni lista real en `/requests` (placeholder de `US-017`); el shell y las tabs son de `US-030`. `S-07` pertenece **nominalmente a `US-023`** (tabla de pantallas de `Backlog.md`, y `US-023` la desarrolla entera: cards, orden, reload). Ver `D2`.

### 1.2 Narrativa

El backlog formula `US-020` por criterios. La intención la fijan `EP-07`, `FR-VIS-001`–`FR-VIS-003` y `SC-09`: el manager abre su cola y ve **solo** lo que espera su decisión — las solicitudes `Submitted` de sus asignados, nunca las de otros managers, nunca las ya decididas, nunca las suyas propias; y el mismo endpoint, llamado por un empleado, devuelve solo lo suyo. El filtro es una decisión del servidor a partir del rol autenticado — el cliente no puede pedirle otra cosa (`FR-AUT-010`, la exigencia nombrada por el sponsor como criterio de aceptación del proyecto).

### 1.3 Criterios de aceptación — verbatim (`Backlog.md` §EP-07 · `US-020`)

| # | Criterio |
|---|---|
| `AC1` | "Given a signed-in manager, when `GET /requests` is called, then I receive the `Submitted` requests of the employees assigned to me." |
| `AC2` | "Given a submitted request belonging to another manager's employee, when I list, then it is absent." |
| `AC3` | "Given a request in a final state, when I list as a manager, then it is absent from my queue." |
| `AC4` | "Given my own request, when my queue renders, then it is absent — a manager never sees their own request in the queue." |
| `AC5` | "Given a signed-in employee, when the same endpoint is called, then only their own requests are returned; the filter is decided server-side by role." |

Contrato del endpoint, verbatim de `FRD.md` §6.3 fila 6:

> **`GET /requests`** · Success `200`: `[{ id, absenceType: { id, code, name }, startDate, endDate, reason, state, employee: { id, fullName }, createdAtUtc, approval?: { responsibleManagerName, decision, comment, decidedAtUtc } }]` · "The `employee` block is present so a manager can see whose request it is; for an employee it is always themselves."

Errores: solo `VF-AUT-004` `401` (`FR-AUT-011`). Sin parámetros de query, sin paginación, sin sort configurable — *"The caller cannot influence this through parameters"* (`FR-VIS-001`).

## 2. Cambios estructurales / de base

**No se requieren cambios de esquema, migraciones, configuración, variables de entorno, permisos, feature flags ni dependencias nuevas.** Las dos consultas leen columnas existentes (`Requests.EmployeeId`, `Requests.State`, `Employees.ManagerId`) y el índice `(EmployeeId, State)` que las sirve existe desde la migración `AddRequests` — `SAD.md` §7.2 lo anota expresamente para estas consultas. `ErrorStatusMap` tampoco cambia (ningún código nuevo). Los puertos crecen (tres interfaces de `Application/Abstractions`), pero son cambios **aditivos**: ningún consumidor existente se ve afectado.

## 4. Casos de uso y tabla de trazabilidad

Caso de uso único de Application: **listar las solicitudes visibles para el usuario autenticado** (`ListVisibleRequestsHandler`), consumido por `GET /api/requests`. Actor: cualquier usuario autenticado; el **rol decide el conjunto** (Employee → propias; Manager → propias ∪ `Submitted` de asignados) sin que ningún parámetro del cliente pueda influir (`FR-AUT-010`/`FR-VIS-001`). ## 7. Riesgos y preguntas abiertas

> ⚠️ **Pregunta abierta para el usuario (no bloquea el arranque — bloquea la forma final de la rama Manager del handler):**
> `AC1` leído en solitario sugiere que el manager recibe **solo** la cola; `FR-VIS-001` dice verbatim que recibe la cola **"plus their own requests as an employee"**, y `US-024` (My Requests del manager, mismo endpoint único del FRD) necesita esas propias. Este plan sigue el FRD (`D3`): **respuesta = unión, y la pantalla `S-07` deriva la cola filtrando `employee.id != usuario actual`**. **¿Se confirma esa lectura?** Dos alternativas si no: (a) cola-pura para el rol Manager (rompe `US-024` salvo que se añada un endpoint no contemplado en el FRD); (b) mantener la unión pero añadir un discriminador explícito al contrato (p. ej. `isOwn: boolean`) para que el cliente no dependa de comparar ids — aditivo, pero se aparta del contrato literal de §6.3.

| Riesgo | Mitigación |
